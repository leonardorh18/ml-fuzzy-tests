O que é fuzz testing

Gerar milhares de entradas até alguma quebrar o sistema

O fuzzer cria entradas novas, aleatórias ou mutando exemplos, roda o sistema e observa. Entradas que exploram partes novas viram base para as próximas.

Modelos usados

Dois classificadores de imagem e um tokenizer de texto

ResNet-50

Para que serve: reconhecer o objeto de uma foto (cachorro, carro, xícara) entre 1000 classes.

Como: rede convolucional de 50 camadas; filtros detectam bordas, texturas e formas.

ViT-Base

Para que serve: a mesma tarefa da ResNet, com as mesmas 1000 classes.

Como: corta a imagem em quadrados de 16×16 pixels e usa atenção, a técnica dos modelos de linguagem.

Tokenizer DistilBERT

Para que serve: quebrar texto em pedaços (tokens) e trocar cada um por um número que o modelo entende.

Por que testar: todo texto passa por ele; um erro aqui afeta tudo depois.

Como geramos os testes

Mutar, verificar, guardar o que explora mais

Imagens (ResNet, ViT)

  1. Muta uma imagem: ruído, brilho, contraste, rotação, blur ou patch
  2. Limita a mudança a 0,08 por pixel
  3. Falha se a classe prevista mudar
  4. Guarda o mutante se ativar neurônios novos

Tokenizer (Atheris)

  1. Gera texto Unicode e um max_length
  2. Guarda entradas que executam código novo
  3. Falha se: lançar exceção, passar do max_length, gerar id inválido ou decode/encode não estabilizar

Sem acesso ao Hugging Face: modelos com pesos aleatórios, imagens sintéticas e vocabulário local.

Conclusão

O pipeline funciona; os números ainda não medem os modelos reais

  • Com pesos aleatórios, a ResNet sempre responde a mesma classe e o ViT está quase indeciso
  • Cobertura de neurônios não ajudou a achar falhas
  • No tokenizer, o fuzzing só funciona onde o Atheris enxerga o código

Próximo passo: rodar com os pesos reais do Hugging Face e fotos de verdade.
