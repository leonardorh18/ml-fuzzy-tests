What is fuzz testing

Feeding a system generated inputs until something breaks

Instead of writing test cases by hand, a program (the fuzzer) generates thousands of inputs automatically and observes how the system behaves.

Classic example

A PDF reader receives thousands of slightly corrupted files. One of them crashes the program: a bug found before a user, or an attacker, finds it.

1. Generate an input

at random, or by mutating an existing one

2. Run the system

and record what it exercised

3. Check: did it fail?

the rule that decides is the oracle

4. Keep it if it explored something new

guided by coverage; repeat thousands of times

Fuzz testing means testing with inputs that are generated automatically and in bulk. The classic example is a file reader: the fuzzer corrupts valid files in thousands of ways until one of them crashes the program. Modern fuzzers such as AFL and libFuzzer are coverage-guided: they record which parts of the program each input executed and keep the inputs that reached new code, so that they can mutate them further. Two concepts will appear throughout the talk: the oracle, which decides whether a failure occurred, and coverage, which guides the search.
