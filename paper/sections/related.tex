\section{Background and Related Work}\label{sec:related}

Our approach combines four lines of work that developed largely in separate communities: grammar-based fuzzing, differential testing, metamorphic testing, and the testing of LLMs. We review each line, then compare the approaches along the dimensions that determine what a test campaign can conclude: how inputs are generated, how valid they are, which oracle judges the output, and whether the result is reproducible.

\subsection{Grammar-Based Fuzzing and Grammar Coverage}

Random fuzzing produces inputs that most structured programs reject at the parser, so the code behind the parser is rarely exercised. Grammar-based fuzzers derive syntactically valid inputs from a grammar instead. LangFuzz, a black-box fuzzer driven by a context-free grammar and fragments of existing test programs, found 105 severe vulnerabilities in Mozilla's JavaScript interpreter in three months \citep{holler2012langfuzz}. Validity has a price: a grammar only generates the structures its author anticipated. When the internals of the system cannot be observed, coverage of the input grammar itself can guide generation toward structures not yet tried. \citet{havrikov2019kpath} formalized $k$-path coverage of a grammar, and the \code{GrammarCoverageFuzzer} of \emph{The Fuzzing Book} \citep{zeller2024fuzzingbook} prefers expansions not yet used, which corresponds to 1-path coverage and is the direct basis of our generator. These fuzzers target formal languages, whose grammar is the specification of valid input. Natural language has no such grammar, so a prompt grammar does not describe the input space of a chat model; it describes a chosen family of requests. A prompt can be well formed by our grammar and still be ambiguous for a model, a distinction we return to in Section~\ref{sec:method}.

\subsection{Differential Testing}

Differential testing gives the same input to several systems that should behave alike and treats divergence as a failure \citep{mckeeman1998differential}. Its strength is that it needs no specification; its weakness is that a divergence is meaningful only if the systems are supposed to agree. Csmith addressed this for C compilers by generating only programs without undefined behavior, so that every disagreement indicates a bug; it found more than 325 previously unknown bugs, and every compiler tested both crashed and silently generated wrong code \citep{yang2011csmith}. DeepXplore brought the idea to deep learning, using several models with the same function as cross-referencing oracles that need no labels, and searching by gradient for inputs that maximize both disagreement and neuron coverage \citep{pei2017deepxplore}. Chat LLMs share no formal specification and are trained differently, so a disagreement among them is a signal rather than a verdict, and a disagreement does not identify the faulty model. Work on hallucination detection shows the complementary risk: cross-checking a model against other models catches errors that self-consistency misses, but models can also be consistently wrong \citep{zhang2023sac3}, in which case the differential oracle is silent.

\subsection{The Test-Oracle Problem and Metamorphic Testing}

Deciding whether an output is correct is the test-oracle problem \citep{barr2015oracle}. Barr et al.\ distinguish specified oracles, derived oracles such as metamorphic relations, and implicit oracles such as crashes; free-form chatbots are an extreme case because specified oracles are rarely available. Metamorphic testing \citep{chen1998metamorphic} sidesteps the problem by checking relations between the outputs of related inputs. In NLP, CheckList generates tests from templates and checks invariance under meaning-preserving changes; in a user study, practitioners who used it created twice as many tests and found almost three times as many bugs \citep{ribeiro2020checklist}. For LLMs, METAL generates hundreds of metamorphic relations from templates to test quality attributes such as robustness \citep{hyun2024metal}; \citet{cho2025metamorphic} collected 191 metamorphic relations for NLP tasks and ran about 560 thousand metamorphic tests on three LLMs; and MORTAR extends metamorphic testing to multi-turn dialogue systems, finding 51\% more bugs per test case than the best single-turn method across eight systems \citep{guo2026mortar}. All of these frameworks compare a model with itself. A violated relation shows inconsistency but not which output is wrong, and a satisfied relation can hide a consistently wrong answer.

\subsection{Testing LLMs and Chat Models}

Most LLM fuzzing targets security. GPTFuzzer mutates human-written jailbreak templates and reaches attack success rates above 90\% against ChatGPT and Llama-2 \citep{yu2023gptfuzzer}; its oracle is a classifier that judges whether the attack succeeded. \citet{wang2024survey} review 102 studies on LLMs in software testing, nearly all of which use LLMs to test other software rather than test the LLMs themselves. NLP research, meanwhile, documents functional weaknesses that a test generator can target. Meaning-preserving formatting changes can shift accuracy by up to 76 points, and this sensitivity persists with larger models and instruction tuning \citep{sclar2024formatting}. Models that know how their tokens are spelled still fail to manipulate text at the character level, for example to reverse or count letters \citep{edman2024cute}. These findings come from static benchmarks evaluated mostly on models of 7\,B parameters or more.

Testing LLMs also differs from testing deterministic programs. Sampling makes outputs vary between runs, providers update hosted models without notice, and generation parameters such as temperature and the token limit change the output. A discrepancy can therefore stem from the decoding configuration or the deployment rather than from the model, and a test campaign must either control these factors or repeat each test enough times to separate them. We control them: local models, pinned revisions, and greedy decoding make every reply reproducible on a given software stack.

\subsection{Comparison and Positioning}

Table~\ref{tab:related} contrasts representative approaches. Grammar- and template-based generators (LangFuzz, CheckList, METAL) guarantee input validity but limit diversity to what their authors wrote; mutation-based generators (GPTFuzzer) explore more freely but can drift from the intended task. Oracles trade generality for decisiveness: differential and metamorphic oracles apply to any input but only flag suspicious behavior, whereas ground-truth oracles decide correctness but only exist for tasks whose answer can be computed. Cost and reproducibility follow from the system under test: DeepXplore needs gradients, hosted LLMs charge per request and change over time, and local models with greedy decoding are cheap to rerun and deterministic.

To our knowledge, no prior work combines a context-free prompt grammar with grammar-coverage guidance, a cross-model differential oracle, and a cross-paraphrase metamorphic oracle for open chat models. Each ingredient has a canonical precedent: the \code{GrammarCoverageFuzzer} for generation, Csmith and DeepXplore for the differential oracle, and CheckList for the invariance oracle. What the combination adds is that each grammar derivation carries its own expected answer. This lets us settle disagreements between models and, more importantly for this study, measure how often the differential and metamorphic oracles would have been right without that answer. The price is scope: the approach only covers tasks whose answer can be computed from the generated values.
