\section{Methodology}\label{sec:method}

Our tool, \code{chatfuzz}, has four parts: a grammar-based prompt generator, chatbot clients, oracles, and an analysis stage that applies the differential and metamorphic relations. All code and unit tests are in the project repository.

\subsection{Test Case Generation}

Each test case starts from a \emph{skeleton}: a task category and randomly drawn values, such as the operands of an arithmetic expression. Because the values are stored, every test case knows its expected answer. A context-free grammar then derives the wording of the request. Deriving the same skeleton several times yields \emph{paraphrases} that must receive the same answer. The grammar has one start symbol per category (Table~\ref{tab:categories}).

\midrule
\code{arith} & \emph{What is 4 multiplied by 101? Give only the numeric result.} & last integer in the reply equals the result \\
\code{count} & \emph{How many times does the letter 'e' appear in the word 'referrer'?} & integer equals the true count \\

Operands mix one-digit, three-digit, six-digit, and negative numbers. Letters for \code{count} are drawn mostly from the word and sometimes from outside it, so that the expected count is zero. The \code{echo} and \code{edge} payloads include combining emoji, right-to-left script, zero-width characters, ligatures, markup, and a 300-character repetition.

\subsection{Coverage-Guided Expansion}

When a nonterminal has several expansions, the generator chooses an expansion that has not yet been used with probability $b$ (\code{coverage\_bias}, 0.8 by default), and a uniformly random one otherwise. This follows the grammar coverage fuzzer of \citet{zeller2024fuzzingbook} and corresponds to 1-path grammar coverage \citep{havrikov2019kpath}. Grammar coverage is the fraction of all (nonterminal, expansion) pairs used so far. Paraphrases of a skeleton must differ in their words, not only in whitespace.

\subsection{Chatbot Clients}

Models are addressed as \code{local:<model>} or \code{api:<model>}. Local models are downloaded from the Hugging Face Hub and run with the \code{transformers} library, using the model's own chat template and greedy decoding, so that each prompt has a single deterministic reply. The API client sends OpenAI-compatible chat completion requests to the Hugging Face Inference Providers router. Runtime errors, timeouts, and malformed replies are recorded as data rather than raised. A reply that stops at the token limit is flagged as truncated.

\subsection{Oracles and Analysis}

The analysis applies three kinds of oracle:
\begin{enumerate}
  \item \textbf{Ground-truth oracles} check each reply against the expected answer of its category (Table~\ref{tab:categories}) and extract a \emph{canonical answer}: an integer, a normalized string, the sorted key list of a JSON object, or a Boolean for \code{echo}.
  \item \textbf{Differential oracle.} The same prompt is sent to every model. Different canonical answers produce a \emph{differential disagreement}, which names the models that are wrong when the expected answer is known; a model that fails at runtime while others reply produces a \emph{differential error}. When all models give the same wrong answer, the analysis reports a \emph{consensus-wrong} prompt, a case that a purely differential oracle cannot detect \citep{zhang2023sac3}.
  \item \textbf{Metamorphic oracle.} For each model, the paraphrases of one skeleton must yield the same canonical answer; otherwise the tool reports a \emph{metamorphic inconsistency}.
\end{enumerate}

The tool reports, per model, the pass rate by category, metamorphic consistency, pairwise disagreement between models, and the number of runtime errors and truncated replies.
